**项目**：两篇论文的复现——EMT（ECCV 2022，有官方代码）与 RTSR（WCNC 2023，重点复现）
**周期**：2026-10-12 ~ 2026-10-21
**环境**：WSL2 Ubuntu 24.04 / Python 3.12（`emt-env`）/ PyTorch 2.5.1+cu121 / RTX 4060 Laptop 8 GB

## 一、项目概述

本项目复现两篇内容感知视频超分（SR）方向的论文，它们构成一条完整的技术链路：

| 论文 | 定位 | 解决什么 | 我的工作 |
|---|---|---|---|
| **EMT**（ECCV 2022） | **有代码**，基础篇 | 为每段视频快速生成专属 SR 模型，避免逐段从头训练 | 跑通官方代码 + 完整实验矩阵 + 与 baseline 对比 |
| **RTSR**（WCNC 2023） | **重点复现** | 把"内容感知 SR"落到 5G-Advanced 的 XR 传输：传 LD 帧 + 专属模型，省流量、提容量 | 算法层两张表 + 网络层仿真 + 容量扫描，从零搭建 |

两篇的关系：**EMT 解决"怎么快速得到专属模型"，RTSR 解决"在真实网络里怎么传、能省多少"**。
本项目的 RTSR 算法层直接复用 EMT 阶段准备的 VSD4K 视频数据与 LR 生成流程。

## 二、论文一：EMT（ECCV 2022，有代码）

### 2.1 论文核心思想

内容感知 SR 的痛点是"每个视频片段都要单独训练一个模型"，训练耗时无法接受。
EMT 用**元学习 + 梯度掩码**：先在一个大规模数据集上学到"如何快速适应新视频"的初始参数，
再对每段视频只更新 **1%–20% 的参数**，从而在保持画质的同时把微调时间压到原来的 1/3。

### 2.2 复现内容与代码对应

| 论文环节 | 复现动作 | 代码位置 |
|---|---|---|
| 元学习（MAML 式训练） | 50 epochs，DIV2K 800 训练 / 100 验证 | `src/trainer_maml.py`，`src/meta_learning_local.sh` |
| 元调优（逐段微调） | MG1–MG4 四段链式微调（lol / sport / dance 三类视频） | `src/meta_tuning_local.sh`、`meta_tuning_mg4.sh`、`meta_tuning_sport.sh`、`meta_tuning_dance.sh` |
| PSNR 优先采样 | 生成每帧每 patch 的 PSNR 排序表 | `psnr_map/`（495 文件、416,941 个 patch 位置），`trainer_maml.py::test_pn()` |
| 梯度掩码 | 按 p_mask 选择要更新的参数 | `src/generate_mask.py`、`src/trainer_gradmask.py` |
| 采样策略消融 | 均匀采样 vs PSNR 优先采样 | `src/meta_tuning_uniform.sh` |
| Meta-Tuning baseline | 全模型微调作为对照 | `src/baseline_metatuning.sh` |
| 数据准备 | DIV2K + VSD4K 下载解压、LR 生成 | `generate_lr.py`、`README.md` 数据章节 |

**代码改动（相对官方仓库）**：
1. 适配 8 GB 显存的训练脚本（batch/patch 调整）；
2. 修复 `main.py` 的 Trainer 选择与训练循环缩进；
3. 删除 `option.py` 中重复的 `--adafm` 参数注册；
4. 新增本地化脚本（`*_local.sh`）与 baseline 脚本。

### 2.3 复现结果

| 实验 | 结果 |
|---|---|
| 元学习（50 epochs） | 最佳 PSNR **32.252** |
| 元调优 lol（MG1→MG4，find_mask） | 33.638 / 33.607 / 34.362 / 33.841 |
| 元调优 lol（MG1→MG4，grad_mask） | 32.609 / 32.640 / 33.187 / 32.794 |
| 多视频验证 sport（grad_mask） | 43.383 / 44.410 / 42.708 / 43.454 |
| 多视频验证 dance（grad_mask） | 37.875 / 37.288 / 36.899 / 37.287 |
| 采样消融（均匀 → PSNR 优先） | 32.588→32.609、32.620→32.640、33.164→33.187（稳定 **+0.02 dB**） |
| Meta-Tuning baseline（全量微调） | 32.903 / 33.069 / 33.818 / 33.455 |
| 效率对比 | EMT **4 s** vs 全量微调 10 s，**约 2.5×**，只更新 1%–20% 参数 |

### 2.4 与论文数值的协议差异

本地 32.6 dB 与论文 39.56 dB 的差距**来自协议，不是实现**：

| 项 | 本复现 | 论文 |
|---|---|---|
| 源视频长度 | 15 s / 495 帧 | 45 s |
| 元调优轮数 | 每段 2 epochs | 未公开，更多 |
| 元学习轮数 | 50 | 未公开 |
| backbone | ESPCN（官方默认） | 论文自选结构 |
| 评估帧 | 与调优同段 | 独立验证集 |

**在同协议下可比的结论**：EMT 用 1%–20% 的参数、约 1/2.5 的时间，换到 **−0.3 dB** 的精度——
这正是论文"高效元调优"的核心 claim。

## 三、论文二：RTSR（WCNC 2023，重点复现）

### 3.1 论文核心思想

XR 高清视频（2K/4K、30–120 FPS、5–10 ms 时延）在 NR 网络上极耗带宽。RTSR 提出：
**服务器只传低清（LD）帧 + 一个专属 SR 模型，UE 用模型在本地把 LD 还原成高清（HD）**。
配合 ①轻量模型选型、②在线训练（周期性更新模型）、③分层 QoS（模型流可牺牲、视频流不可），
论文声称可省 **最高 50% 流量**、提升 **约 40% 容量**。

### 3.2 算法层复现（Table I / Table II）

**Table I：模型尺寸 ↔ 画质**（EDSR，x2，29 轮，训练帧 1-400 / 评估 401-495）

| 模型 | 块/特征 | 尺寸 | 论文 PSNR | 本地 540p→1080p | 本地 1080p→2160p @5 Mbps |
|---|---|---:|---:|---:|---:|
| M1 | 8 / 9 | 62.6 KB | 33.22 | 33.057 | 41.501 |
| M2 | 8 / 26 | 506.9 KB | 35.78 | 35.702 | 42.295 |
| M3 | 16 / 64 | 5351 KB | 36.03 | 39.216 | 42.833 |

**核心发现**（本复现最重要的一条）：每翻倍尺寸的 PSNR 增益随任务难度单调下降——

| 变化 | 540p→1080p | 4K 干净 bicubic | 4K @3–5 Mbps | 论文 |
|---|---:|---:|---:|---:|
| M2→M3 | 1.033 | 0.275 | **0.179** | **0.075** |

即：**压缩退化把容量收益压平了**。论文"M2 是性价比拐点"的结论，第一次被解释清楚——
不是模型不够大，而是任务里存在不可逆的压缩失真。

**Table II：码率 ↔ 质量**（论文原始设置 1080p@3–5 Mbps → 2160p）

| LD 码率 | 本地 PSNR | 本地 VMAF | 论文 PSNR | 论文 VMAF |
|---:|---:|---:|---:|---:|
| 2994 kbps | 41.047 | 88.61 | 31.83 | 83.55 |
| 3966 kbps | 41.830 | 90.23 | 33.02 | 87.71 |
| 4947 kbps | 42.295 | **90.99** | 33.91 | **90.09** |

**VMAF 与论文几乎重合**（90.99 vs 90.09），这是复现可信度的最强证据。
PSNR 高 6–8 dB 的根因是内容不同（论文用实拍赛车/游戏，本机 YouTube 不可达，改用 CG 动画）。

**代码对应**：
- `run_table1.sh` / `run_table1_4k.sh`：一键跑三档模型；
- `run_table2.sh` / `run_table2_4k.sh`：码率扫描 + 通用模型基线；
- `tools/encode_ld{,_4k}.sh`：x264 两遍编码（540p 与 1080p 两套码率）；
- `tools/make_vmaf.py`：导出 SR/HR 序列并用 libvmaf 算分；
- `tools/collect_table1/2.py`：自动汇总成 markdown 表；
- `tools/bench_latency.py`：单帧时延实测。

### 3.3 网络层复现（ns-3 + 5G-LENA）

**代码对应**：`RTSR/rtsr-simulation.cc`（改自 5G-LENA 的 `cttc-nr-traffic-3gpp-xr.cc`）

| 论文机制 | 实现方式 |
|---|---|
| 双流（视频 + 模型） | 新增 SR 模型流：530 KiB / 6 s、UDP 端口 5000 |
| 分层 QoS | 视频 → `NGBR_LOW_LAT_EMBB`（5QI 80）；模型 → `NGBR_VIDEO_TCP_DEFAULT`（5QI 9） |
| QoS 调度 | `NrMacSchedulerTdmaQos` + `NrMacSchedulerLcQos` |
| 拥塞环境 | 5–100 MHz 可配带宽、RLC 缓冲 500 KiB |
| 多小区 | 新增 `--numSites`，六边形排布、就近接入、真实邻区干扰 |
| 统计 | FlowMonitor 逐流字节/时延，`calc_traffic_saving.py` 做 per-UE 流量账 |

**实测结果（60 s、5 MHz、3 UE）**

| 流 | 投递率 | 平均时延 |
|---|---|---|
| XR 视频（高优先级） | **99.3%** | ~450 ms |
| SR 模型（低优先级） | **89.7%** | ~668 ms |

**流量账（每 UE，ΔT=6 s，模型 530 KiB）**

| 项 | 数值 |
|---|---:|
| LD 视频（实测 5.09 Mbps） | 38.16 MB |
| SR 模型（10 次更新） | 5.32 MB |
| RTSR 合计 | **43.48 MB** |
| 传统 HD（假设 LD×2） | 76.31 MB |
| **节省** | **43.0%** |

ΔT 敏感性：2 s → 29.7%、6 s → 43.2%、10 s → 45.9%、30 s → 48.6%、**60 s → 49.3%**。
即论文的"最高 50%"对应 **ΔT ≈ 30–60 s**（模型几乎不更新的静态场景）。

**容量扫描**（`capacity_sweep.py`）

| 场景 | 视频投递率 | 时延 | 满意 UE |
|---|---:|---:|---:|
| 5 MHz，3 UE | 99.5% | 344 ms | 80% |
| 5 MHz，6 UE | 0% | — | 0% |
| 100 MHz，3–24 UE | 100% | 2 ms | 100% |
| 20 MHz，15 UE（1 小区） | 64.9% | 797 ms | 4% |
| 20 MHz，15 UE（7 小区） | **94.2%** | 260 ms | 56% |

其中 100 MHz 下最有价值的一条：**UE 从 12 增到 24 时，SR 模型投递率从 88.8% 掉到 36.4%，
而视频始终 100%/2 ms** —— "牺牲模型保视频"第一次被定量观察到。

### 3.4 四条核心结论

1. **VMAF 与论文重合**（90.99 vs 90.09），复现可信；
2. **压缩退化压平容量收益**（0.275 → 0.179 → 0.075），解释了论文的模型选型；
3. **"选 M2"是传输决策**：M3 的模型开销在 ΔT=6 s 时占 **73%** 带宽，M2 只占 7%；
4. **分层 QoS 有效**：拥挤时优先丢模型流，视频体验不受影响。

### 3.5 三组额外发现（论文未涉及）

| 发现 | 数字 |
|---|---|
| 压缩的代价可量化 | 干净 45.37 dB → 3 Mbps 41.05（−4.32）→ 5 Mbps 42.30（−3.07） |
| 纯 PyTorch 达不到实时 | M2 @2160p 218.6 ms（4.6 FPS）；1080p 52.8 ms（18.9 FPS） |
| 多小区是净收益 | 20 MHz/15 UE：7 小区 94.2% vs 单小区 64.9% |

### 4.2 一键复现

```bash
# EMT 元学习 + 元调优
cd src && bash meta_learning_local.sh && bash meta_tuning_local.sh

# RTSR 算法层
cd ~/code/EDSR-PyTorch
bash run_table1.sh          # Table I（540p→1080p）
bash run_table2.sh          # Table II（6 个码率 + 通用基线）
bash run_table1_4k.sh       # Table I（1080p→2160p）

python3 capacity_sweep.py --bandwidth 100 --numerology 1 --ues 3
python3 calc_traffic_saving.py --ns3-log /tmp/rtsr_ns3.log --ues 3
```

### 4.3 工程质量

- **全部结果由脚本生成**，不手填数字：`collect_table1/2.py`、`collect_dt.py`、`calc_traffic_saving.py`、`capacity_sweep.py`；
- **文档一致性有检查器**：`check_consistency.py` 校验 15 个关键数字的跨文档一致性，并扫描 7 个历史错误值；
- **可复现性**：`requirements-lock.txt` 锁定依赖，所有实验的 `config.txt` / `log.txt` 保留；
- **偏差声明**：每份数据表都写明与论文的口径差异（分辨率、内容、码率缩放、业务模型）。

## 五、局限（主动说明）

1. **内容不同**：论文用实拍赛车/游戏素材，本机 YouTube 不可达，改用 CG 动画 → PSNR 高 6–11 dB；
2. **分辨率**：算法层同时跑了 540p→1080p 与 1080p→2160p，只有后者与论文一致；
3. **网络层规模**：7 小区（非论文的 21 cell wraparound），未实现帧级 PDB，满意度用投递率近似；
4. **业务模型**：3GPP XR 混合业务约 5 Mbps/UE，论文是 10–20 Mbps/UE 的固定码率视频；
5. **实时性**：纯 PyTorch FP32 下 2160p 输出仅 4.6 FPS，未做量化/图优化；
6. **EMT**：AdaFM / Sidetuning 两个 baseline 未复现。
